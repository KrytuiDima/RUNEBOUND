Core Combat & Drawing Mechanic

The full pipeline from pointer event → gesture recognition → 3D spell instantiation → damage resolution

Mechanical Design Math-Heavy

1A — 2D Canvas Overlay → 3D World Space Projection

The drawing input happens on a transparent HTML Canvas overlay layered on top of the Three.js WebGL canvas. This separation is intentional — it keeps pointer event capture isolated from the 3D render loop and avoids performance interference from input polling inside requestAnimationFrame.

Coordinate Pipeline

1
Pointer Event Capture (CSS Layer)
Overlay canvas captures pointerdown, pointermove, pointerup with pointerId for multi-touch. Coordinates are in pixel space: (clientX, clientY).
CLIENT
2
Normalize to NDC Space [-1, 1]
Convert pixel coords to Normalized Device Coordinates. This is renderer-resolution-independent.
NDC
3
Raycaster → Drawing Plane Intersection
A THREE.Raycaster projects from camera through the NDC point. It intersects an invisible DrawingPlane — a THREE.Plane positioned at the player's cast anchor (1.8 units in front of player, perpendicular to camera forward vector).
WORLD
4
World Point → Local Rune Space
Transform the world-space intersection point into the player's local coordinate system using the inverse model matrix. This ensures runes are evaluated relative to the player's facing direction, not global axes.
LOCAL
5
Stroke Buffer Accumulation → Recognition Trigger
Points accumulate in a rolling buffer. Recognition fires on pointerup OR when gap between points exceeds 180ms (auto-complete). Buffer max: 256 points, oldest discarded beyond 3 seconds.
BUFFER
// ─── COORDINATE PIPELINE ─────────────────────────────────────
class DrawingInputManager {
  constructor(renderer, camera, playerObject) {
    this.renderer   = renderer;
    this.camera     = camera;
    this.player     = playerObject;
    this.raycaster  = new THREE.Raycaster();
    this.strokeBuffer = [];
    this.isDrawing  = false;

    // DrawingPlane: 1.8 units in front of player, faces camera
    this.drawPlane = new THREE.Plane();
    this.planeTarget = new THREE.Vector3();
  }

  _updateDrawingPlane() {
    // Face the plane toward camera, offset 1.8m forward from player
    const dir = new THREE.Vector3();
    this.camera.getWorldDirection(dir);
    const planeOrigin = this.player.position.clone()
      .addScaledVector(dir, 1.8)
      .setY(this.player.position.y + 1.4); // chest height
    this.drawPlane.setFromNormalAndCoplanarPoint(
      dir.negate(), planeOrigin
    );
  }

  onPointerMove(e) {
    if (!this.isDrawing) return;
    const canvas = this.renderer.domElement;
    // ① NDC Conversion
    const ndc = new THREE.Vector2(
      ( (e.clientX - canvas.offsetLeft) / canvas.clientWidth  ) * 2 - 1,
      -((e.clientY - canvas.offsetTop)  / canvas.clientHeight) * 2 + 1
    );
    // ② Cast ray from camera through NDC point
    this.raycaster.setFromCamera(ndc, this.camera);
    const worldPt = new THREE.Vector3();
    this.raycaster.ray.intersectPlane(this.drawPlane, worldPt);
    if (!worldPt) return;
    // ③ Transform to player-local space
    const invMatrix = this.player.matrixWorld.clone().invert();
    const localPt = worldPt.applyMatrix4(invMatrix);
    // ④ Push to buffer with high-resolution timestamp
    this.strokeBuffer.push({
      x: localPt.x, y: localPt.y,
      t: performance.now()          // sub-millisecond precision
    });
  }
}

1B — Gesture Recognition: Modified $1 Unistroke Algorithm

The standard $1 Unistroke Recognizer (Wobbrock et al.) is adapted for web performance with three key optimizations: reduced sample count, Web Worker offloading, and an EarlyOut threshold to skip poor matches without full comparison.

⚠ Latency Budget Recognition must complete within 16ms (one 60Hz frame) so spell feedback is imperceptible. The raw $1 algorithm at N=64 samples costs ~4ms on desktop. On mobile (slower JS engines) this spikes to 18–30ms — hence the Web Worker + N=32 optimization.

// ─── MODIFIED $1 RECOGNIZER (Web Worker context) ────────────
// Optimized: N=32, EarlyOut, pre-rotated templates, WASM optional

const N = 32;               // sample count (halved from original 64)
const SQUARE_SIZE = 250.0;   // bounding box for scale normalization
const ORIGIN = {x:0, y:0};
const PHI = 0.5 * (-1.0 + Math.sqrt(5.0)); // golden ratio
const ANGLE_RANGE = 45;      // ±45° search window (deg)
const ANGLE_PRECISION = 2;   // degrees (coarser = faster)
const EARLY_OUT_SCORE = 0.95;// skip remaining templates if hit
const MATCH_THRESHOLD = 0.65;// minimum accept score

function recognize(points, templates) {
  points = resample(points, N);
  const radians = indicativeAngle(points);
  points = rotateBy(points, -radians);
  points = scaleTo(points, SQUARE_SIZE);
  points = translateTo(points, ORIGIN);

  let best = { score: -Infinity, name: 'NONE' };

  for (const tmpl of templates) {
    // EarlyOut: skip if best is already near-perfect
    if (best.score >= EARLY_OUT_SCORE) break;
    const d = distanceAtBestAngle(
      points, tmpl.points,
      -ANGLE_RANGE, +ANGLE_RANGE, ANGLE_PRECISION
    );
    const score = 1.0 - (d / (0.5 * Math.sqrt(2 * SQUARE_SIZE ** 2)));
    if (score > best.score) best = { score: score, name: tmpl.name };
  }
  return best.score >= MATCH_THRESHOLD
    ? { match: best.name, confidence: best.score }
    : { match: 'UNRECOGNIZED', confidence: best.score };
}

// Golden Section Minimum Search for best rotation angle
function distanceAtBestAngle(pts, tmpl, a, b, threshold) {
  let [x1, x2] = [a + PHI*(b-a), b - PHI*(b-a)];
  let [f1, f2] = [pathDist(rotateBy(pts,x1),tmpl), pathDist(rotateBy(pts,x2),tmpl)];
  while (Math.abs(b-a) > threshold) {
    if (f1 < f2) { b=x2; x2=x1; f2=f1; x1=a+PHI*(b-a); f1=pathDist(rotateBy(pts,x1),tmpl); }
    else            { a=x1; x1=x2; f1=f2; x2=b-PHI*(b-a); f2=pathDist(rotateBy(pts,x2),tmpl); }
  }
  return Math.min(f1, f2);
}

// Web Worker dispatch — returns Promise
function recognizeAsync(strokePoints) {
  return new Promise((resolve) => {
    recognizerWorker.postMessage({ type: 'RECOGNIZE', points: strokePoints });
    recognizerWorker.onmessage = (e) => resolve(e.data);
  });
}
🔵 Latency Handling The recognizer runs inside a dedicated Web Worker so it never blocks the main thread render loop. The round-trip cost (main→worker→main) adds ~0.5ms of message-passing overhead. On average devices, total recognition latency is 3–8ms for N=32. Meanwhile, the client immediately starts rendering a "casting charge-up" VFX so the player never perceives dead time — visual feedback precedes server confirmation by design.

1C — Drawing Quality Score (QS): The Core Balancing Variable

Every completed stroke produces a Quality Score (QS) in range [0.0, 1.0]. This is the master variable passed to all downstream systems: damage calculation, mana cost, cast time, and critical hit probability. QS is computed from four sub-scores, each weighted differently:

Quality Score Composite Formula
QS = (S_smooth × 0.30) + (S_close × 0.20) + (S_tempo × 0.30) + (S_conf × 0.20) All sub-scores ∈ [0, 1]. Weighted to reward smooth, correctly-paced drawing over closure alone.
S_smooth = 1 − ( σ_curvature / MAX_CURV_VAR ) σ_curvature = std-dev of angular change between consecutive point-triples. MAX_CURV_VAR = 2.8 rad²
S_close = 1 − clamp( dist(P₀, Pₙ) / bbox_diagonal, 0, 1 ) Only applied to rune types tagged as CLOSED_FORM. Open runes use S_close = 1.0 always.
S_tempo = exp( −λ × |T_actual − T_ideal| / T_ideal ) where λ = 3.0 T_ideal = rune's base cast time (e.g., Flame Rune = 0.8s). Gaussian decay penalizes too-fast AND too-slow.
S_conf = recognizer_confidence (from $1 algorithm output, range 0.65→1.0, normalized) Normalized: (raw_score − 0.65) / 0.35. Scores below 0.65 are already rejected.

Curvature Smoothness Calculation

function computeSmoothnessScore(points) {
  const angles = [];
  for (let i = 1; i < points.length - 1; i++) {
    const v1 = { x: points[i].x   - points[i-1].x, y: points[i].y   - points[i-1].y };
    const v2 = { x: points[i+1].x - points[i].x,   y: points[i+1].y - points[i].y   };
    const dot = v1.x*v2.x + v1.y*v2.y;
    const mag = Math.sqrt((v1.x**2+v1.y**2)*(v2.x**2+v2.y**2)) || 1e-6;
    angles.push(Math.acos(Math.max(-1, Math.min(1, dot/mag))));
  }
  const mean   = angles.reduce((s,v) => s+v, 0) / angles.length;
  const sigma2 = angles.reduce((s,v) => s+(v-mean)**2, 0) / angles.length;
  return Math.max(0, 1 - (sigma2 / 2.8));
}

Skill Tree & RPG Progression

Three meta-paths that alter HOW the player draws — not what they cast

Game Systems Progression Design

Runebound has no traditional classes. Instead, Inscription Paths modify the drawing system itself — they change tolerance thresholds, recognition parameters, and the spatial grammar available to the player. A character fully invested in one path plays mechanically different from another, not just numerically different.

2A — The Three Inscription Paths

⚡ PATH I: FLUX (The Velocity Scribes)

Masters of speed-drawing who sacrifice precision for cadence. Flux mages maintain Momentum Stacks — consecutive successful spells multiply their next spell's damage, but any missed draw breaks the chain.

Core Mechanic Change: The $1 recognizer's required sample count decreases as Flux rank increases, meaning fewer input points are needed for a valid recognition. At max rank, a 3-point stroke can trigger a fire bolt.

Cast SpeedRank 5: +55%
Peak DamageRank 5: −25% solo
Momentum MultiplierMax Stack ×3.2
🎯 PATH II: ETCHER (The Calligraphers)

Precision draw-mages who sculpt each rune with clinical exactness. Etchers gain an Etch Lock mechanic: if their QS exceeds 0.88 three times in a row, their next cast becomes a free "Phantom Etch" — bypassing the draw entirely and casting at QS=1.0.

Core Mechanic Change: Critical hit damage scales from the standard ×2.0 to ×2.0 + (QS − 0.85) × 6.0, making a 1.00 QS score deal ×2.9 crit damage. They also unlock "Pressure Sensitivity" — tablet stylus pressure maps to a bonus quality sub-score.

Crit Multiplier (max)×2.90
Cast Speed−20% vs Flux
Mana EfficiencyRank 5: −35% cost
🔷 PATH III: GEOMANCER (The Architects)

Shape-based mages who abandon freehand gesture recognition entirely. Geomancers activate a Grid Overlay that snaps their strokes to geometric vertices. Spell power scales with the complexity of the polygon drawn: Triangle = tier 1, Hexagram = tier 3, Nonagon inscribed with inner star = tier 5.

Core Mechanic Change: The $1 algorithm is replaced with a Polygon Detector that counts vertices, calculates interior angles, and checks for nested shapes. Geomancers also unlock Persistent Rune Anchors — drawn shapes stay in the 3D world for 8 seconds as field-control traps.

2B — Core Attributes: Mana, Stability, Resonance

The three RPG attributes directly modify the drawing system in mathematical ways, not just stat bars. They are the bridge between the RPG layer and the gesture-input layer:

Mana — The Fuel
MaxMana = 80 + (Level × 12) + (INT × 4.5) + PathBonus Base regen: 3.5/sec out of combat, 1.2/sec in combat. High QS reduces ManaCost: see Module 1D formula.
ManaRegen = 3.5 × (1 + INT × 0.008) × CombatModifier CombatModifier: 1.0 out-of-combat, 0.34 in-combat.
Stability — The Tolerance Modifier
DrawTolerance = 0.15 × (1 + STAB / 200) × PathMult STAB range: 0–100. At STAB=100: tolerance = 0.2275 (52% wider acceptance window).
QS_floor = max(0, STAB × 0.003) STAB provides a minimum QS floor — even a terrible draw isn't complete garbage. At STAB=80: QS can never fall below 0.24, preventing total mana waste.
Resonance — The Synergy Amplifier
ResonanceAmp = 1.0 + (RES × 0.015) Solo: ResonanceAmp scales spell damage. RES=60 → ×1.90 damage baseline.
SynergyContrib = QS_player × ResonanceAmp × SynergyTypeBonus In group synergy casts (Module 3B), each player's contribution is weighted by their RES. A high-RES Geomancer (+40% synergy bonus from Path) can contribute disproportionately to group spells.
PhaseCoherence = exp(−0.5 × (Δt_sync / RES_Window)²) Δt_sync = time diff between player stroke completions. RES_Window = 0.5 + (avg_RES_party / 200) seconds. High party RES widens the sync window, making synergy spells more forgiving to time.

2C — Drawing Tolerance System

Tolerance is the angular deviation budget within the $1 recognizer's final score-to-match comparison. It determines how "close" a drawing must be to the template. Without Stability investment, even slightly sloppy drawings fail — with high Stability they gracefully degrade to lower QS rather than hard-failing.

// When player targets an InscriptionSocket, re-orient DrawingPlane
function alignDrawingPlaneToSocket(socket, playerPos) {
  const socketNormal = socket.getWorldNormal(); // e.g., wall face outward
  const socketOrigin = socket.getWorldPosition();
  // Offset slightly toward player to avoid z-fighting
  const toPlayer = playerPos.clone().sub(socketOrigin).normalize();
  const adjustedOrigin = socketOrigin.addScaledVector(toPlayer, 0.05);
  drawingPlane.setFromNormalAndCoplanarPoint(socketNormal, adjustedOrigin);
  // Constrain drawing area to socket bounds (prevent out-of-bounds strokes)
  drawingConstraintAABB = socket.getBoundingBox2D(socketNormal);
}

Puzzle State Machine: Multi-Glyph Sequences

Complex dungeon puzzles use a GlyphSequence object that requires runes to be drawn in order. Each glyph in the sequence has an optional time-window: the player must draw all runes within T_sequence seconds, or the sequence resets. This creates real-time pressure without requiring combat.

GlyphSequence {
  required: [ "Sol", "Bind", "Flow", "Sol" ],    // ordered list
  currentIndex: 0,
  timeLimit: 12.0,                               // seconds for full sequence
  timer: null,
  tolerance_override: 0.55,                      // puzzles can set custom min QS

  onRuneDrawn(runeType, qs):
    if qs < tolerance_override: return FAIL_QUALITY
    if runeType != required[currentIndex]: return FAIL_ORDER → resetSequence()
    currentIndex++
    resetTimer(timeLimit)
    if currentIndex == required.length: return SEQUENCE_COMPLETE → triggerEffect()

  onTimerExpired(): resetSequence()   // partial progress lost
}

Network & Multiplayer Logic

Authoritative server model, anti-cheat via temporal entropy analysis, and projectile state synchronization

Security-Critical Architecture

4A — Authoritative Server Architecture

The server is the sole truth-holder for all spell resolution. Clients send raw input evidence; the server re-validates and computes outcomes. This prevents macro injection, instant-draw exploits, and damage amplification hacks.

What Data Is Actually Sent Over the Wire

🔴 CRITICAL DESIGN DECISION Never send pre-resolved spell outcomes from client to server. A client saying "I just cast Flame Rune at QS=0.95" is trivially fakeable. Instead, the client sends the raw stroke point stream with timestamps. The server runs its own copy of the recognizer and QS calculator. This doubles compute but is non-negotiable for integrity.

Binary Wire Format (production optimization)

In production, the JSON above is replaced with a packed binary format using FlatBuffers (schema-defined). A typical 24-point stroke compresses from ~720 bytes (JSON) to ~92 bytes (FlatBuffers binary). This matters at 40 players each drawing 2–3 spells per second in a dungeon fight.

namespace Runebound.Net;

  x: float16;    // 2 bytes — NDC range [-1,1], 0.001 precision
  y: float16;    // 2 bytes
  t: uint16;     // 2 bytes — ms offset, max 65s
}

table StrokeSubmit {
  player_id:       uint32;
  stroke_id:       uint16;
  points:          [StrokePoint];
  stroke_duration: uint16;
  input_entropy:   float16;
  client_ts:       uint48;
  target_id:       uint32;
  pos_x: float16; pos_y: float16; pos_z: float16;
  yaw:   float16;
}

4B — Anti-Cheat: Temporal Entropy Analysis

A macro program drawing runes will produce strokes with unnaturally uniform point spacing and velocity. Human tremor and speed variance creates a distinct statistical signature. The server validates this using three independent checks:

Check 1: Point Interval Entropy

Compute the Shannon entropy of the inter-point time intervals. Human drawing has high entropy (variable speed). Macros have low entropy (uniform timing).

Formula: H = −Σ p(Δt_i) × log₂ p(Δt_i) over discretized time bins

Threshold: H < 1.8 bits → flag as suspicious. H < 1.2 bits → immediate reject + log.

Check 2: Duration Plausibility Gate

Stroke duration must fall within biologically plausible range. A 32-point stroke cannot be drawn faster than ~120ms (human motor limit). Any stroke under 110ms for >8 points is auto-rejected.

Formula: min_duration = N_points × 3.5ms + rune_complexity_offset

Context: Flux Path Rank 5 reduces minimum by 30% — stored server-side per player.

Check 3: Velocity Profile Matching

Real human strokes follow a bell-curve velocity profile: slow start, peak speed, deceleration. Macros often inject linear velocity. Server fits a Gaussian to the velocity sequence and checks R² fit score.

Threshold: R² < 0.35 → macro flag. Combined with Check 1: flag adds to player's suspicious score. At score >= 3: temporary cast lock + report queue.

// ─── SERVER-SIDE ANTI-CHEAT VALIDATION ─────────────────────
function validateStroke(packet, playerRecord) {
  const { points, strokeDuration, inputEntropy } = packet;

  // Gate 1: Point count sanity
  if (points.length < 4 || points.length > 256)
    return { valid: false, reason: 'POINT_COUNT_OOBOUNDS' };

  // Gate 2: Duration plausibility
  const pathMult = playerRecord.fluxRank >= 5 ? 0.70 : 1.00;
  const minDuration = points.length * 3.5 * pathMult;
  if (strokeDuration < minDuration)
    return { valid: false, reason: 'SUPERHUMAN_SPEED' };

  // Gate 3: Timestamp consistency (cross-check with server receive time)
  const recvLatency = Date.now() - packet.clientTs;
  const declaredDelta = points.at(-1).t - points[0].t;
  if (Math.abs(declaredDelta - strokeDuration) > 50)
    return { valid: false, reason: 'TIMESTAMP_TAMPER' };

  // Gate 4: Entropy check (client-computed, server spot-verifies)
  const serverEntropy = computeIntervalEntropy(points);
  if (Math.abs(serverEntropy - inputEntropy) > 0.3)  // tampered entropy field
    flagPlayer(playerRecord.id, 'ENTROPY_MISMATCH');
  if (serverEntropy < 1.2)
    return { valid: false, reason: 'MACRO_SIGNATURE' };

  // Gate 5: Velocity Gaussian fit (soft check)
  const r2 = computeVelocityGaussianFit(points);
  if (r2 < 0.35) incrementSuspicion(playerRecord.id, 1);

  // All gates passed: run gesture recognition on server
  const result = recognize(points, MASTER_TEMPLATE_LIBRARY);
  const qs     = computeQualityScore(points, result.confidence, strokeDuration);
  return { valid: true, rune: result.match, qs, r2 };
}

function computeIntervalEntropy(points) {
  const deltas = points.slice(1).map((p,i) => p.t - points[i].t);
  const bins = new Map();
  deltas.forEach(d => {
    const bin = Math.floor(d / 5);   // 5ms bins
    bins.set(bin, (bins.get(bin) || 0) + 1);
  });
  const total = deltas.length;
  let H = 0;
  bins.forEach(count => {
    const p = count / total;
    H -= p * Math.log2(p);
  });
  return H;
}

4C — State Synchronization for Magical Projectiles

Magical projectiles are fast-moving entities (20–60 m/s in world units) that must appear smooth on all clients despite network jitter. The architecture uses a server-authoritative simulation at 20Hz with client-side interpolation for non-owned entities and extrapolation for owned projectiles.

Entity Snapshot Model (Colyseus StateSync)

// SERVER — 20Hz tick loop
function gameTick(dt = 50ms) {
  for proj in activeProjectiles:
    proj.position += proj.velocity * dt
    proj.velocity  *= (1 − proj.drag * dt)   // air resistance
    checkCollisions(proj)
    if proj.hit: resolveHit(proj); removeEntity(proj)

  // Broadcast snapshot to all room clients
  broadcastSnapshot({
    tick: currentTick,
    entities: getDeltaState(lastAckedTick)  // only changed entities
  })
}

// CLIENT — 60Hz render loop
function renderFrame(dt) {
  const renderTime = serverTime() - 100ms  // interpolation buffer

  for proj in localProjectiles:
    if proj.isOwned:
      // Owned: extrapolate from latest server state + elapsed time
      proj.renderPos = proj.serverPos + proj.velocity * (renderTime - proj.serverTime)
    else:
      // Non-owned: interpolate between two known server snapshots
      const [s0, s1] = getSnapshotBracket(renderTime)
      const alpha = (renderTime − s0.t) / (s1.t − s0.t)
      proj.renderPos = lerp(s0.pos, s1.pos, alpha)

// Lag Compensation for hit detection (server-side rewind)
function resolveHitWithLagComp(hitEvent, playerLatency) {
  const rewindTick = currentTick - Math.ceil(playerLatency / 50)
  const historicState = getStateAtTick(rewindTick)   // ring buffer
  const hit = checkCollisionIn(historicState, hitEvent.projectile, hitEvent.target)
  if hit: applyDamage(hitEvent.target, hitEvent.damage)
}

Critical Implementation Note: The Drawing Mode UI Contract

When the player enters Drawing Mode, the game must temporarily suspend camera input (mouse/touch events that normally drive camera rotation). This requires a clear UI state machine with three states: EXPLORING (camera control active, drawing canvas hidden), DRAWING (canvas active, camera locked, overlay visible), and CASTING (canvas hidden, spell animation playing, brief camera unlock delay). The transition is triggered by holding a dedicated key/button, never automatic. Accidental draw activation while moving is the #1 onboarding frustration to eliminate.
